The problem

Two 4-link planar arms sharing a workspace have an 8-dimensional configuration space, and the valid part of it is mostly thin: a sampled configuration is valid only if no arm self-intersects, the arms do not touch each other, and neither touches an obstacle. Sampling that space directly is how a planner spends a whole budget without finding anything. Multilevel (bundle-space) planning attacks it by solving an easier problem first: plan for 1-link arms, then use that solution to bias the search for 2-link arms, and so on up to the full chain. Each level is a projection of the next, so a lower-level solution is a prefix of a higher-level one.

Architecture

  • One C++17 CLI (mlmp) on OMPL 1.7.0.
  • Solver::solve(const RunOptions&) -> RunResult does no I/O, so the same function backs the CLI, the trace recorder and the WebAssembly entry point.
  • One mlmp.run/1 JSON object on stdout per run, and an mlmp.trace/1 JSONL stream per traced run.
  • The browser build is the same sources through Emscripten (Dockerfile.wasm), single-threaded on purpose so it needs no COOP/COEP headers.
  • 469 034 B + 22 445 B gzip -9 for mlmp.wasm + mlmp.mjs — 9.4% of the repository's 5 MiB payload gate — and it runs at ≈0.65× native throughput (measured, BiQRRT/scene1/seed 42/10 s: 8 104 vertices native vs 5 379 in the browser).

— The Emscripten port, the two viewers, and the URDF path (serial-chain flattening, FCL narrowphase, 0.02 rad collision step)

QRRT grows one tree per bundle level outward from the start and reaches the goal through random sampling and the level's findSection() lift. BiQRRTImpl subclasses BundleSpaceGraph and keeps two nearest-neighbour structures per level, treeStart_ and treeGoal_. Each grow() call swaps the active tree, samples the bundle, clips the extension to maxDistance_, steers, adds the new vertex to the active tree — and then tries to steer straight from it to its nearest neighbour in the other tree. A successful steer adds that edge and marks the level solved. Both trees exist at every level of the hierarchy, so the bidirectional search and the multilevel decomposition compose rather than compete.

What the visualizations show

Three pictures of the same run, because a planner is three different things at once.

The motion

The default view plays the solution as the arms themselves, interpolated in joint space by the same wrap-aware rule (KinematicChainSpace::interpolate) the motion validator checked each segment under — so every pose on screen is one the checker accepted, not a guess between waypoints. It matters: on scene1 the straight workspace lines an earlier version drew between the four simplified path states missed the true tip curve by up to 0.083 units on a scene 1.09 wide, about 46 px at a 600 px canvas.

The search

Every vertex is one configuration the planner actually committed to, drawn at the chain tip of the links its bundle level owns — read one level at a time, because all four at once is 37 000 overlapping dots and no information. BiQRRT tags its two trees itself, so blue and red are the planner's own bookkeeping; QRRT tags nothing, so the binary derives the same labels by breadth-first search from the start and goal vertices over the frame's edges, and every frame records which of the two it was (tree_source: planner or derived). The purple findSection() configurations exist whether or not a run ever solves.

The configuration space itself

A bundle level whose dimension is two — level 0 of a two-robot scene, level 1 of a one-robot scene — can be drawn exactly: both axes are joint angles over [−π, π], and the grey region is computed by running the real collision predicate over a grid, the same segment-intersection test the C++ checker uses. The tree appears there in the space it is actually searched in, and configurations from higher levels project into the same square, because that projection is what a bundle space is.

What is measured, and what is not

  • scene1 BiQRRT solved 2/3 at a 10 s budget, seeds 41–43
  • scene5 BiQRRT solved 3/3 at a 10 s budget, seeds 41–43
  • scene4, scene6 solved 0/3 by both BiQRRT and QRRT

Those are stopwatch observations on one host, not a benchmark, and there is a known confound: BiQRRTImpl::setup() pins the extension step to 0.1 when no caller sets a range, while QRRT's SelfConfig default measured 1.78–3.55 across scene1's levels, so part of any gap may be step size rather than bidirectionality. Making that a declared parameter with a scale-derived default, and then running a real campaign with confidence intervals, is Track F and Phase 2 of the roadmap.

Both rows moved when the collision-resolution defect below was fixed: scene1 used to solve 3/3 and first solutions arrived six times sooner. Those were paths whose interiors had barely been checked, so the older, faster numbers measured a different problem.

Until then this repository claims no planner is faster than another.

A defect the playback found

Animating a returned solution turned up something no number in the output reported: the paths contained poses that collide. Every path state was valid — the viewer re-checks them with a port of the C++ predicate and they all pass — but the arms swept through an obstacle between two valid states: 22 of 73 interpolated poses on scene1/BiQRRT, 0.049 units deep, 27 px on a 600 px canvas.

The cause was a units mismatch. OMPL sizes its motion-validator step as 1% of the state space's bounds extent — 17.77 rad over eight joints — while this space's distance is a workspace measure scaled by the 0.1 link length. One scene1 path segment measured 0.17 against a 0.178 step and received exactly one interior collision check while both arms swung across the obstacle field.

KinematicChainSpace::validSegmentCount now derives the count from the motion itself: rotating joint j by Δθ moves everything beyond it by at most (n−j)·linkLength·|Δθ|, which bounds the swept displacement of any point on the arm, and the step is a fifth of the scene's shortest obstacle edge. The deepest penetration left on a scene1 solution is 0.0004 units — 0.2 px — the epsilon any discrete checker has: the recording the loop above plays grazes an obstacle on 1 of its 121 drawn poses, against 22 of 73 before. Both viewers re-check every pose they draw and colour the rejects red, so this cannot quietly come back.

Run it yourself

docker run --rm ghcr.io/tomsabala/mlmp:latest --algo BiQRRT --input-file scene1.json --time-limit 10

--algo BiQRRT --input-file ur5_scene1.json --time-limit 2 plans a 6-DOF UR5 in joint space with FCL collision checking and prints model: "urdf", dof: 6.
